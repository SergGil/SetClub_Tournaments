# Досягнення/бейджі гравця (план, не реалізовано)

## Контекст

Ідея зі списку "свіжих ідей" (поза `docs/DESIGN_ROADMAP_2026.md`, який покриває 7 пунктів
конкурентного дослідження — усі вже реалізовані). Профіль гравця (`/players/[id]`) уже показує
багато глибокої статистики (рейтинг Glicko-2/OpenSkill з історією, Set Club бали, head-to-head
матриця), але немає жодного легкого, "приємного" шару зверху — усе подається як таблиці й числа.
Беджі — дешевий спосіб додати трохи гейміфікації, використовуючи дані, які вже порахувані.

## Дизайн

**Без нової моделі БД (v1).** На відміну від `RatingSnapshot` (кешована таблиця, бо рейтинг —
дорогий ітеративний розрахунок), беджі рахуються з уже завантажених на сторінці даних —
той самий підхід, що `summarizePlayerStats` (`src/lib/player-stats.ts`) і
`buildHeadToHeadMatrix` (`src/lib/head-to-head.ts`): чиста функція, нуль побічних ефектів,
нуль інвалідації кешу. Якщо пізніше стане дорого — можна кешувати окремо, але для клубу цього
масштабу (десятки, не тисячі гравців) це навряд чи знадобиться.

**Каталог беджів (v1, орієнтовний):**

| Бедж | Умова | Джерело даних |
|---|---|---|
| Дебют | зіграв перший завершений матч | `MatchPlayerRow` (уже є) |
| Перша перемога | перша перемога в завершеному матчі | те саме |
| Серія перемог (3+/5+) | N перемог поспіль за датою (`scheduledDate`/`completedAt`) | ті самі рядки, відсортовані за датою |
| Фіналіст | грав матч з `round === FINAL_ROUND` (`src/lib/playoff-rounds.ts`) | `Match.round` |
| Чемпіон | виграв матч з `round === FINAL_ROUND` | те саме + `winnerSide` |
| Резидент клубу | зіграв у N різних турнірах (`tournamentsPlayed`) | вже рахується в `PlayerStats` |
| Вбивця фаворитів | виграв матч, де сам був андердогом за `buildMatchPreview` (ймовірність < 50%) | `src/lib/rating/match-preview.ts` — але прогноз рахується "наперед" для запланованих матчів, а не заднім числом для завершених → треба новий виклик `winProbability`/`winProbabilities` на рейтингу гравців **до** цього матчу, не поточному (складніше за інші пункти, можна відкласти на v2) |

**Де показати.** Ряд компактних іконок/чіпів на профілі гравця, під картками статистики
(`StatCard`, `src/components/stat-card.tsx`) і над рейтинговою секцією — не окрема сторінка,
щоб не роздувати навігацію. Кожен бедж — іконка + підпис при наведенні/тапі з поясненням умови
(і, де можливо, датою здобуття). Незароблені беджі можна або не показувати зовсім (мінімалістичний
варіант), або показати сірим "заблокованим" — вирішити при реалізації разом із власником продукту.

**Обсяг тестування.** Кожна умова — чиста функція від `MatchPlayerRow[]`/`Match[]`, легко покрити
юніт-тестами (`*.test.ts`) так само, як `player-stats.test.ts`.

## Код/файли (орієнтовно)

- `src/lib/achievements.ts` (+ `.test.ts`) — `buildPlayerAchievements(playerId, rows, matches)`,
  чиста функція, повертає масив `{ id, label, description, earnedAt? }`.
- `src/components/player-badges.tsx` — рендер ряду чіпів з тултипами.
- `src/app/players/[id]/page.tsx` — підключення нового блоку, дані вже завантажені на сторінці
  (не потрібен новий запит для базових беджів; "вбивця фаворитів" — виняток, якщо додавати).

**Скоуп v1**: тільки одиночний формат тенісу спершу (найпростіші дані), доробити падел і парний
формат окремим кроком — той самий підхід поетапного розширення, що вже застосовувався для
рейтингу/прогнозу.

## Відкриті питання

1. Показувати незароблені беджі як "заблоковані" (мотивує) чи ховати (менше шуму)?
2. "Вбивця фаворитів" вимагає рейтинг гравця *на момент* матчу, а не поточний — цінна фіча, але
   дорожча за решту; варто в v1 чи відкласти?
3. Чи потрібні беджі й на мобільному застосунку одразу, чи спершу web (як з іншими фічами з
   `DESIGN_ROADMAP_2026.md`, де мобільний наздоганяв web окремим спринтом)?
