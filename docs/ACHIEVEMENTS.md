# Досягнення/бейджі гравця

## Контекст

Ідея зі списку "свіжих ідей" (поза `docs/DESIGN_ROADMAP_2026.md`, який покриває 7 пунктів
конкурентного дослідження — усі вже реалізовані). Профіль гравця (`/players/[id]`) уже показував
багато глибокої статистики (рейтинг Glicko-2/OpenSkill з історією, Set Club бали, head-to-head
матриця), але без жодного легкого, "приємного" шару зверху. Беджі додають трохи гейміфікації,
рахуючись з уже наявних даних матчів.

Каталог і всі пороги узгоджені з користувачем по кожному пункту окремо перед реалізацією:

## Каталог беджів (v1)

| Бедж | Умова |
|---|---|
| Дебют | зіграв перший завершений матч |
| Перша перемога | перша перемога в завершеному матчі |
| Серія | 3 перемоги поспіль |
| Гаряча серія | 5 перемог поспіль |
| Фіналіст | грав матч з `round === FINAL_ROUND` |
| Чемпіон | виграв матч з `round === FINAL_ROUND` |
| Резидент клубу | зіграв у 20+ різних турнірах |
| Вбивця фаворитів | виграв матч, де суперник/суперниця мали ≥80% шансів на перемогу за рейтингом **до** цього матчу |

**Формати.** Усі беджі рахуються одразу по всіх чотирьох комбінаціях формат×спорт (одиночний/парний
× теніс/падел) — одна людина, один набір бейджів, не окремо на теніс і окремо на падел. Серія
перемог і "резидент клубу" також комбіновані: перемога в падел-турнірі одразу після тенісної
рахується як продовження тієї самої серії.

## Дизайн

**Без нової моделі БД.** Беджі рахуються з уже завантажених на сторінці/у запиті даних — той самий
підхід, що `summarizePlayerStats` (`src/lib/player-stats.ts`) і `buildHeadToHeadMatrix`
(`src/lib/head-to-head.ts`): чиста функція, нуль побічних ефектів, нуль інвалідації кешу.

**"Вбивця фаворитів" — розширення рейтингового рушія.** `computeSinglesRatingsWithHistory`/
`computeDoublesRatingsWithHistory` (`src/lib/rating/engine.ts`) вже реплеять всю історію матчів і
на кожному кроці тримають під рукою рейтинг обох сторін *до* матчу (`winnerPre`/`loserPre` для
одиночного, `teamA`/`teamB` до `updateDoublesMatch` для парного) — тому й ймовірність перемоги
переможця "заднім числом" рахується практично безкоштовно, без окремого проходу по даних. Обидві
функції тепер повертають третє поле `upsets: MatchUpsetCheck[]` (`{ matchId, winnerIds,
winnerPreWinProb }`) поряд із `final`/`snapshots`. Оскільки `engine.ts` спільний для тенісу й
падела (обидва `ratings-data.ts`/`padel-ratings-data.ts` викликають ті самі функції), розширення
запрацювало для обох спортів одразу — нових `getUpsetWins`/`getPadelUpsetWins` доданo по одній
функції-обгортці на файл.

**Де показано.** Компонент `PlayerAchievements` (`src/components/player-achievements.tsx`) —
ряд чіпів одразу під заголовком профілю, над картками статистики. Незароблені беджі показані
"заблокованими" (сірий фон, іконка замка) — рішення користувача, мотивує показом того, чого ще не
досягнуто, а не приховує. Кнопка "Сховати"/"Показати" згортає весь блок; стан — `localStorage`
(`setclub:achievements-hidden`), per-viewer перевага, не серверний стан.

## Код/файли

- `src/lib/rating/engine.ts` — `MatchUpsetCheck`, `upsets` у поверненні
  `compute{Singles,Doubles}RatingsWithHistory`.
- `src/lib/rating/ratings-data.ts`, `src/lib/rating/padel-ratings-data.ts` — `getUpsetWins`/
  `getPadelUpsetWins(matchType)`.
- `src/lib/achievements.ts` (+ `tests/lib/achievements.test.ts`) — `toAchievementMatchInput`
  (нормалізує один сирий матч будь-якого спорту/формату в позицію гравця), `buildGiantKillerMatchIds`
  (зводить club-wide upset-списки в набір id матчів для одного гравця),
  `buildPlayerAchievements` (чиста функція → масив `Achievement`).
- `src/components/player-achievements.tsx` — UI: чіпи + кнопка сховати/показати.
- `src/app/players/[id]/page.tsx` — підключення: додатковий запит падел-матчів гравця
  (`getPlayerPadelMatches`) і чотирьох upset-списків, побудова `achievementInputs`, рендер.
- `src/app/api/v1/players/[id]/achievements/route.ts` — той самий розрахунок у форматі JSON для
  мобільного застосунку (без `sport`/`matchType` — беджі завжди комбіновані).
- `src/app/api/v1/players/me/route.ts` — новий, окремий роут: `{ player }` гравця, залінкованого
  на поточний обліковий запис (`getPlayerByUserId`). Потрібен для мобільної іконки "Мій профіль".
- `tests/lib/rating/engine.test.ts` — тести на `upsets` для обох рушіїв.

### Мобільний застосунок

У мобільному застосунку не було жодного екрана перегляду профілю гравця (лише адмінське
редагування) — довелось створити новий, а не портувати наявний UI.

- `mobile/src/app/(tabs)/rating/[id].tsx` — новий екран: ім'я гравця + ті самі чіпи досягнень
  (спрощений варіант, без решти статистики профілю — це окремий, більший обсяг роботи на
  майбутнє).
- `mobile/src/app/(tabs)/rating/index.tsx` — рядки таблиці рейтингу стали натискними (`Link` →
  `/rating/[id]`).
- `mobile/src/app/(tabs)/profile/index.tsx` — іконка (`trophy-outline`) "Мій профіль і досягнення"
  для залогіненого користувача з залінкованим гравцем (`useMyPlayer`) — той самий вхід, що аватар
  у веб-хедері (`IdentityLink`, `src/components/nav.tsx`), тільки явною іконкою замість аватара.
- `mobile/src/features/players/api.ts`/`types.ts` — `useMyPlayer`, `useAchievements`, тип
  `Achievement`.
- `mobile/src/lib/achievements-storage.ts` — кнопка "сховати" тепер зберігається між сесіями
  через `@react-native-async-storage/async-storage` (новий пакет, встановлений через
  `npx expo install`, сумісна з Expo SDK 57 версія) — не `expo-secure-store`, той зарезервований
  для токена сесії (`session-storage.ts`), а не для несекретних UI-переваг. Той самий підхід, що
  `localStorage` у веб-версії (`player-achievements.tsx`), тільки асинхронне читання при монтуванні
  екрана замість синхронного.
- Повний профіль гравця (статистика, head-to-head, графік рейтингу — як на вебі) на мобільному
  **не** реалізовано — це окрема, значно більша фіча.

### Після code-review

- `useMyPlayer` тримав кеш під фіксованим ключем `['players','me']`, не прив'язаним до акаунту —
  на спільному пристрої вхід іншого користувача протягом 60с після виходу попереднього міг
  показати чужого залінкованого гравця (застосунок ніде не чистить react-query кеш при виході).
  Ключ тепер включає `session.user.id`.
- `/api/v1/players/[id]/achievements` не перевіряв існування гравця — неіснуючий id мовчки
  повертав порожній список "не зароблено" замість 404. Додано перевірку через `getPlayerById`.

Ще дві речі, спершу задокументовані як "свідомо не чіпав", потім усе-таки виправлені за проханням
користувача:

- **Подвійний реплей рейтингової історії.** `getSinglesRatings()`/`getUpsetWins("SINGLES")`
  (і парні/падел-аналоги) обидва запускали власний повний `computeXRatingsWithHistory` над тими
  самими рядками — по два незалежні проходи на формат при кожному відкритті профілю. Виправлено
  через `cache()` з `"react"` (той самий патерн, що вже є в `getTournamentById`,
  `src/lib/queries/tournaments.ts`): `getSinglesHistoryReplay`/`getDoublesHistoryReplay` (і падел-
  версії) рахують один раз за запит, `getSinglesRatings`/`getUpsetWins`/їхні парні й падел-аналоги
  ділять результат. Публічні сигнатури не змінились — жоден інший виклик (`/rating`, `/leaderboard`
  і т.д.) не торкнувся.
- **Сортування бейджа "Серія" в межах одного дня.** Раніше — лише за `playedAt` (дата, не час),
  тож кілька матчів одного дня фактично сортувались за порядком запису в масиві. Додано другий
  ключ `enteredAt` (`completedAt ?? createdAt`, реальний timestamp з точністю до секунди — порядок,
  у якому рахунки реально збережені) — не гарантія справжнього порядку гри (адмін може внести
  результати дня не по порядку), але значно кращий за довільний, і це реальний сигнал, а не
  вигадка. `AchievementMatchInput.enteredAt` — новe поле, `playedAt` для показу дати бейджа лишився
  як був.

### Після третього (глибокого, `xhigh`) code-review

Виправлено:

- **Потрійне дублювання "walkover-стійкого" визначення результату сторони.** Той самий 2-3-рядковий
  предикат (win/loss/null з урахуванням walkover) був незалежно написаний у
  `player-stats.ts::summarizePlayerStats`, `players/[id]/page.tsx::matchResultForPlayer` і
  `achievements.ts::toAchievementMatchInput`. Винесено в `resultForSide` (`src/lib/match-result.ts`,
  + тести), усі три місця тепер викликають її.
- **Каталог із 8 бейджів без компілятор-перевірки повноти.** Масив-літерал не гарантував, що новий
  `AchievementId` в union автоматично матиме відповідний запис — легко забути один запис, і бейдж
  мовчки зникне для всіх. Переписано на `Record<AchievementId, Achievement>` — відсутній ключ тепер
  помилка компіляції, а не тиха прогалина.
- **Немає тесту на реальне злиття тенісних і падел-матчів.** Функції були протестовані лише на
  "чистих" даних одного спорту. Додано тест, що явно змішує тенісо- і падел-подібні сирі матчі й
  перевіряє наскрізну серію перемог через межу спортів.
- **`toLocaleDateString` замість `formatDateKyiv`/`formatDateUTC` для дати бейджа (веб і мобільний).**
  `earnedAt` — мішанина UTC-опівнічних дат (`scheduledDate`) і справжніх таймстемпів
  (`completedAt`/`createdAt`), а `PlayerAchievements` — клієнтський компонент, що гідрується:
  `toLocaleDateString` залежить від таймзони сервера при SSR і таймзони глядача при гідрації,
  ризикуючи показати не той день і/або гідраційний мисматч. Веб — `formatDateKyiv` (уже був у
  `src/lib/date-format.ts`). Мобільний застосунок такого хелпера не мав — додано
  `mobile/src/lib/date-format.ts` з тим самим `Intl.DateTimeFormat(..., { timeZone: "Europe/Kyiv" })`.
- **Мобільний екран профілю плутав мережеву помилку з "гравця не знайдено".** `usePlayer`/
  `useAchievements` не перевіряли `isError` — при збої мережі/500 екран мовчки показував "Гравця не
  знайдено" замість зрозумілої помилки. Тепер розрізняє 404 (`ApiError.status === 404`) від будь-
  якої іншої помилки; секція досягнень окремо показує "Не вдалося завантажити досягнення" при
  власному збої.
- **Перегони (race condition) між читанням `AsyncStorage` і тапом по кнопці "Сховати".** Якщо
  користувач тапав кнопку до того, як асинхронне читання збереженого стану встигало завершитись,
  результат читання міг мовчки скасувати щойно зроблений тап. Додано `useRef`-прапорець: читання
  більше не застосовується, якщо користувач уже сам перемкнув стан.
- **Ще один подвійний прохід рейтингової історії — цього разу прихований у трендах.** Функції
  `getSinglesRatingsTrend`/`getDoublesRatingsTrend` (і падел-аналоги) досі самостійно ганяли
  `computeXRatingsWithHistory` над "поточним" (без виключення) набором рядків — окремо від уже
  кешованого реплею, яким користуються `getSinglesRatings`/`getUpsetWins`. Виправлення виявило
  ще й реальний зайвий SQL-запит (не лише зайвий CPU): `getSinglesHistoryReplay`/
  `getDoublesHistoryReplay` тепер повертають ще й самі вихідні `rows`, і trend-функції беруть їх
  звідти, а не викликають `fetchRatingMatchRows` вдруге (`unstable_cache`, на відміну від
  React-івського `cache()`, не гарантує дедуплікацію в межах одного запиту — тест на
  `getSinglesRatingsTrend`/`getDoublesRatingsTrend` це й підловив: мок `prisma.match.findMany` був
  розрахований лише на один виклик).
- **`getUpsetWins`/`getPadelUpsetWins` — 4 club-wide реплеї при кожному відкритті мобільного
  API-роута досягнень.** На відміну від сторінки профілю (де `getSinglesRatings` і `getUpsetWins`
  ділять один per-request кеш), мобільний `/api/v1/players/[id]/achievements` викликає лише
  `getUpsetWins`/`getPadelUpsetWins` — ділити роботу нема з чим у межах одного запиту, тож без
  крос-запитового кешування кожен перегляд/опитування профілю (60с `staleTime` на мобільному)
  переганяв усі 4 репрея заново. Обидві функції тепер додатково обгорнуті в `unstable_cache`
  (той самий `CACHE_OPTIONS`/тег, що й решта файлу) — на промасі кеша й далі йдуть через
  спільний per-request реплей, на попаданні кеша реплей не запускається взагалі.

Задокументовано без зміни коду (реальні нюанси, але виправлення означало б відхід від уже
усталених конвенцій цього кодбейзу або непропорційне ускладнення):

- **Асиметрія формули ймовірності перемоги для "Вбивці фаворитів".** Glicko-2's `expectedScore`
  враховує лише RD суперника, тож `winProbability(A,B)` і `winProbability(B,A)` не обов'язково
  дають у сумі 1. Але `buildMatchPreview` (`match-preview.ts`) вже трактує їх як доповнення одне
  одного за конвенцією (`probB: 1 - probA`), а не незалежним обчисленням — той самий підхід, що
  й `winnerPreWinProb` тут. Формулювання доку "суперник мав ≥80%" еквівалентне "переможець мав
  ≤20%" саме за цією усталеною конвенцією. Додано пояснювальний коментар біля
  `GIANT_KILLER_MAX_WINNER_PROB`.
- **"До матчу" означає різне для одиночного й парного рушія.** Glicko-2 групує весь турнір в один
  рейтинговий період (усі матчі турніру бачать той самий "перед турніром" знімок), OpenSkill
  оновлюється послідовно по матчу — це наслідує вже задокументоване в `engine.ts` архітектурне
  рішення (немає надійного порядку матчів усередині турніру), не новий баг цієї фічі. Додано
  пояснювальний коментар на `MatchUpsetCheck`.

### Після четвертого проходу — indexed `getUpsetWinsByPlayer`

Пункт "`buildGiantKillerMatchIds` лінійно сканує весь клубний список апсетів на кожен профіль" —
спершу задокументований як "не варте індексації при цьому масштабі", за проханням користувача
таки виправлений:

- `src/lib/rating/ratings-data.ts`, `padel-ratings-data.ts` — нові `getUpsetWinsByPlayer`/
  `getPadelUpsetWinsByPlayer` (`unstable_cache`, той самий тег), кожен апсет проіндексований за
  `playerId` (для парного — під ключами обох переможців). Індекс будується раз на вікно
  ревалідації й переюзається на кожен наступний перегляд профілю/мобільний запит замість
  club-wide сканування щоразу.
- `src/lib/achievements.ts` — `buildGiantKillerMatchIds` тепер приймає
  `Record<playerId, MatchUpsetCheck[]>[]` замість `MatchUpsetCheck[][]` і читає лише запис цього
  конкретного гравця (`index[playerId] ?? []`) — більше не сканує й не фільтрує чужі записи.
- `src/app/players/[id]/page.tsx`, `src/app/api/v1/players/[id]/achievements/route.ts` — виклики
  переведено на нові indexed-функції.
- Нові тести: `getUpsetWinsByPlayer` (індексація парної перемоги під обома переможцями, не під
  переможеними), оновлені тести `buildGiantKillerMatchIds` під нову сигнатуру.
- Дрібні DRY-зауваження (дублювання `try {localStorage...} catch` у трьох компонентах, 4 майже
  однакові `cache()`-обгортки в `ratings-data.ts`/`padel-ratings-data.ts`) — свідомо не займались,
  жодна не є багом.
