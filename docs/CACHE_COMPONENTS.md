# Cache Components: досліджено, не увімкнено

## Контекст

Ручний аудит застосунку виявив, що жоден маршрут ніколи не кешується/не стає статичним —
`next build`'s список роутів не має жодного `○ Static` (крім `/icon`-типу службових). Причина:
`src/components/nav.tsx` (рендериться в кореневому `layout.tsx` на кожній сторінці) викликає
`auth()` — Request-time API — що форсує повністю динамічний рендер для **всього** застосунку.
Уся вже наявна інфраструктура точкової інвалідації (`revalidatePath`/`updateTag(STATS_CACHE_TAG)`
на кожній admin-дії) через це не дає жодного ефекту на кешування сторінок у проді.

Природний фікс — обгорнути `Nav`'s auth-залежну частину в `<Suspense>`, щоб решта сторінки
рендерилась статично, а сесія стрімилась окремо. У Next 15 це працювало через `experimental_ppr`.
**У Next 16 цей прапорець прибрали повністю** — `<Suspense>` сам по собі більше не розблоковує
статичну "оболонку"; єдиний шлях — `cacheComponents: true`.

## Чому не просто увімкнули

Це не "обгорнути `Nav` в Suspense" за складністю. Під `cacheComponents` **будь-яке** читання БД
(не лише `auth()`) за замовчуванням вважається "динамічним" — кожен виклик Prisma в тілі сторінки
блокує миттєвий рендер, доки явно не позначиш `'use cache'` (з `cacheLife`/`cacheTag`) або не
обгорнеш у `<Suspense>`.

Спробував увімкнути (`cacheComponents: true` + офіційний codemod
`cache-components-instant-false`, який ставить `instant = false` на кожну сторінку — безпечний,
без зміни поведінки прийом з докси Next). Перший же реальний `next build` впав на **білд-помилці**
(не м'якому попередженні) на найпростішій сторінці (`/coffee`, просто
`prisma.menuSection.findMany()`, без жодного стосунку до `Nav`):

```
Error: Route "/coffee": Next.js encountered the unstable value
`require('node:crypto').randomBytes(size)` while prerendering.
```

**Причина**: `@neondatabase/serverless` (Neon serverless-драйвер, обгорнутий `@prisma/adapter-neon`)
викликає `crypto.randomBytes` всередині SASL/SCRAM-SHA-256-рукостискання — клієнтський nonce,
обов'язковий раз на кожне НОВЕ з'єднання з Postgres (протокольна вимога безпеки, не код
застосунку). Next бачить цей виклик під час prerender-у й трактує як недетермінізм. `instant =
false` тут не рятує — той прапорець відкладає лише "могло б заблокувати навігацію", а не жорсткі
помилки недетермінізму.

## Що з'ясував емпірично

Обгорнув **одну** функцію (`getActiveMenuSections`, запит `/coffee`) у `'use cache'` і перезібрав —
`/coffee` зникла зі списку помилок; впали інші, незачеплені сторінки (`/tennis`, `/gallery`) з тією
самою помилкою у своїх власних Prisma-викликах. Підтверджує: **`'use cache'` дійсно обходить
проблему**, механічно, для кожної функції окремо — не нефіксована несумісність драйвера.

Усі експериментальні зміни відкотив (`git checkout`) — нічого з експерименту не лишилось у коді,
крім цього запису й короткого коментаря в `next.config.ts`.

## Реальний обсяг (якщо колись повертатись)

Щоб увімкнути `cacheComponents`, **кожна** функція-запит до БД, яку викликає рендер сторінки —
десятки функцій (`src/lib/queries/*`, `src/lib/rating/*`, `tournament-standings.ts`,
`padel-tournament-standings.ts`, `stats.ts` тощо) — має отримати `'use cache'` + `cacheLife` +
свідомо обраний `cacheTag`, зведений з уже наявними `revalidatePath`/`updateTag(STATS_CACHE_TAG)`-
викликами в ~90 server actions, щоб дані й далі коректно оновлювались одразу після дій адміна.
Реальний, розтягнутий у часі проєкт по функції за раз — не конфіг-прапорець.

## Чому не робимо зараз

При трафіку клубу (сотні відвідувачів, не тисячі) виграш — приблизно 50-150мс на закешоване
завантаження сторінки (пропущений DB round-trip). Реальний ефект, але непомітний людині на такому
масштабі. Ціна — не лише сам обсяг міграції, а й **новий клас багів, якого зараз структурно не
може існувати**: неправильно прив'язаний `cacheTag` тихо показує застарілий рахунок/турнірну
таблицю після редагування адміном, замість завжди свіжих даних, які гарантує сьогоднішній
повністю динамічний рендер. Обмін швидкості, якої ніхто не відчує, на новий спосіб показати
неактуальні дані — погана угода на цьому масштабі.

**Повернутись варто**, коли трафік виросте на порядок (а не "клуб трохи побільшав") — наприклад,
якщо SEO/соціальні прев'ю (`docs/SEO.md`) справді почнуть приводити відчутний потік людей ззовні
клубу. Не фіксоване число — рішення за ситуацією, коли питання постане знову.
