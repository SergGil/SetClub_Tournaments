# Рейтинг клубу — Glicko-2 (одиночні) + OpenSkill (парні)

## Контекст

`/leaderboard` (перейменований на "Статистика") показує лише сирі перемоги/поразки — без
урахування сили суперника. Потрібен справжній *рейтинг*: окремий для одиночних і парних матчів
(бо це різні за суттю навички, порівнювати їх напряму не можна), з урахуванням рахунку геймів
(перемога 6:0 6:0 має важити більше за перемогу 7:6 у вирішальному сеті), і зрозумілий для ~20
учасників клубу без технічної підготовки — сторінка `/rating` (зараз заглушка "в розробці") має
пояснювати простою мовою, як рахується число.

Обрані алгоритми: **Glicko-2** для одиночних, **OpenSkill** для парних (не буквальний TrueSkill —
та сама байєсівська ідея командного рейтингу, але без патентних питань Microsoft і з активно
підтримуваним TypeScript-пакетом; узгоджено з користувачем).

## Ключове архітектурне рішення: рахувати "на льоту", без збереження в БД

Рахунок матчу в цьому застосунку **можна редагувати чи видаляти після завершення**, і переможець
може заднім числом змінитись (`saveScoreAction` у `src/lib/actions/matches.ts` завжди видаляє й
пересоздає `MatchSet`, без блокування вже завершених матчів; `updateMatchAction` повністю скидає
матч при зміні складу гравців). Рейтинг, що зберігається і оновлюється інкрементально (по одному
матчу за раз), був би застарілим/неправильним щоразу, коли редагується минулий результат.

`src/lib/stats.ts` вже вирішує цю саму проблему для статистики перемог/поразок: це чиста функція,
яка на кожен запит переграє всі завершені матчі із сирих рядків, обгорнута в `unstable_cache` під
тегом `STATS_CACHE_TAG = "match-stats"`, інвалідованим через `updateTag(STATS_CACHE_TAG)` у кожній
мутуючій server action. Рейтинговий рушій повторює той самий патерн — **перевикористовуємо
`STATS_CACHE_TAG`, без нового тега, без нової Prisma-моделі, без міграції, без backfill-скрипта.**
Рейтинги для всієї існуючої історії матчів автоматично правильні одразу після релізу фічі.

## Урахування рахунку геймів: спільне поняття "dominance"

`src/lib/rating/dominance.ts`:
```ts
export const DEFAULT_DOMINANCE_NO_GAMES = 0.75; // знявся до першого гейму

export function computeDominance(
  sets: { sideAGames: number; sideBGames: number }[],
  winnerSide: "A" | "B",
): number {
  // сумуємо геймів переможця й переможеного по всіх сетах
  // if (winnerGames + loserGames === 0) return DEFAULT_DOMINANCE_NO_GAMES;
  // return Math.max(0.5, winnerGames / (winnerGames + loserGames));
  // клемп потрібен: переможець матчу може мати менше сумарних геймів, ніж переможений
  // (напр. 7-6, 0-6, 7-6 → 14 проти 18 → 0.4375 → клемп до 0.5)
}
```
Результат завжди в `[0.5, 1]`. Матчі зі зняттям (`retired`) не мають окремої обробки — рахуються
повністю, як і зараз у `stats.ts`.

- **Glicko-2 (одиночні)**: замість бінарного результату `s ∈ {0,1}` у формули йде неперервний
  рахунок `s = dominance` для переможця і `1 - dominance` для переможеного (формули коректні для
  будь-якого `s ∈ [0,1]` — це неофіційна, свідома адаптація алгоритму Glickman'а, чесно
  задокументована в коді й у поясненні для гравців).
- **OpenSkill (парні)**: пакет `openskill` v5 має вбудовану підтримку рахунку — `rate()` приймає
  опції `score` (сирий рахунок геймів по сторонах) і `margin` (поріг, нижче якого різниця рахунку
  вважається звичайним варіюванням і не підсилює зміну рейтингу). Переможець матчу передається
  окремо через `rank` (а не виводиться з `score`), бо переможець не завжди має більше сумарних
  геймів (див. клемп у `dominance.ts` для Glicko-2) — важлива деталь, розв'язана так само в обох
  модулях. Підсилення від `margin` впливає лише на mu, sigma від бібліотеки лишається без змін.
  Зміна mu ділиться між партнерами пари **не порівну**, а пропорційно до невизначеності (sigma)
  кожного — новачок у парі "рухається" сильніше за результатом матчу, ніж досвідчений партнер
  поруч (перевірено тестом `openskill.test.ts`, спростувало початкове припущення про "однакову
  зміну для обох"). Про це прямо сказано в поясненні на сторінці.

## Рейтингові періоди / порядок матчів

- **Одиночні (Glicko-2)**: завершені SINGLES-матчі групуються по турніру — один турнір = один
  рейтинговий період, періоди йдуть за `Tournament.startDate` за зростанням. Саме для цього в
  Glicko-2 існують "rating periods" (пакетне оновлення за кілька ігор одразу) — і це елегантно
  обходить те, що матчі всередині одного турніру не мають надійного дрібного порядку (`round` —
  довільний текст, матчі одного рандомайзера мають майже однаковий `createdAt`). Всередині періоду:
  для кожного гравця збираються пари (рейтинг суперника **до періоду**, dominance-рахунок), і
  застосовується один виклик `updateGlicko2Period` — ніяких оновлень усередині періоду по одному
  матчу. Гравець, який раніше грав, але пропустив період, отримує лише "no games"-інфляцію RD;
  гравець без жодного матчу в історії клубу просто не бере участі в розрахунку, поки не зіграє
  перший матч.
- **Парні (OpenSkill)**: у цьому сімействі алгоритмів немає поняття періоду — завершені DOUBLES-
  матчі обробляються послідовно в порядку `(Tournament.startDate, Match.createdAt, Match.id)`,
  команди оновлюються матч за матчем. Свідома асиметрія (чесно проговорена в поясненні): парний
  рейтинг не отримує зростання невизначеності від тривалої перерви, як одиночний.

## Стартові значення й шкала відображення

- Glicko-2: `rating 1500, RD 350, volatility 0.06`, `tau = 0.5` (рекомендований Glickman'ом
  діапазон 0.3–1.2). Показується сирий рейтинг у шкалі ~1500.
- OpenSkill: стартові значення бібліотеки `mu=25, sigma=25/3≈8.33` — перераховуються **лише для
  відображення** (внутрішня математика лишається в рідних одиницях) так, щоб невизначеність нового
  парного гравця візуально відповідала невизначеності нового одиночного:
  `DISPLAY_SCALE = 350 / (25/3) ≈ 42.0`, `displayRating(mu) = 1500 + (mu - 25) * DISPLAY_SCALE`.
- **У таблиці сортування й показ — за "консервативним" рейтингом, не за сирим rating/mu**
  (саморегулює нових/невпевнених гравців без штучного мінімуму матчів — стандартна практика обох
  алгоритмів для публічних таблиць):
  - одиночні: `rating - 2*RD`
  - парні: `displayRating(mu - 3*sigma)` (це власний `ordinal(r, { z: 3 })` з OpenSkill, та сама
    конвенція, що й у таблицях лідерів Xbox Live TrueSkill)

## Урахування сіяності в парному рейтингу (доповнення, узгоджено з користувачем)

При жеребкуванні пар (`RandomizeMatchesButton`) кожна пара формується з одного сіяного і одного
несіяного гравця — тобто адмін заздалегідь знає (через `seed` у `TournamentParticipant`), хто в
парі сильніший, і ця інформація губилася при звичайному sigma-пропорційному поділі зміни рейтингу
між партнерами. Виправлено: коли рівно один із двох партнерів команди сіяний у цьому турнірі,
сіяний отримує **60%** сумарної зміни mu команди (і в плюс за перемогу, і в мінус за поразку),
несіяний — **40%**; сума лишається незмінною (просто інакше розподілена), sigma від бібліотеки не
чіпається. Якщо в парі обидва сіяні, обидва несіяні, або пару склали вручну (заздалегідь визначена
пара, не за правилом сіяний+несіяний) — сигналу немає, і зберігається стандартний
sigma-пропорційний поділ бібліотеки.

Пакет `openskill` v5.0.1 декларує опцію `weight` у типах саме для такого сценарію, але вона ніде не
підключена в жодній із вбудованих моделей (перевірено грепом по `dist/`) — тож застосовано ручний
пост-обробний перерозподіл уже порахованої зміни mu команди (`redistributeBySeed` у
`src/lib/rating/openskill.ts`), той самий підхід, який спочатку планувався для margin-of-victory
до того, як з'ясувалося, що `rate()` має нативну підтримку `score`/`margin`.

Для цього `RatingMatchRow.players` (у `engine.ts`) отримав поле `seeded: boolean` на кожного
гравця (для одиночних не використовується), а вибірка в `ratings-data.ts` додатково тягне
`tournament.participants: { playerId, seed }` і мапить `seed !== null` на кожного гравця матчу.

Пояснено на сторінці `/rating` окремим пунктом інформера: "Чому сіяний партнер отримує більшу
частку зміни рейтингу".

## Структура модулів (нові файли, усі під `src/lib/rating/`)

За патерном `src/lib/randomize-pairs.ts` (+ поруч `.test.ts`): чисті, без звернень до БД,
юніт-тестовані модулі.

1. **`src/lib/rating/dominance.ts`** + `dominance.test.ts` — див. вище. Тести: суха перемога → 1.0,
   один сет 7-6 → ≈0.538, "виграв матч, але менше сумарних геймів" → клемп до 0.5, знявся без
   жодного гейму → 0.75.

2. **`src/lib/rating/glicko2.ts`** + `glicko2.test.ts` — написаний вручну (готові npm-пакети
   Glicko-2 приймають лише бінарний результат win/loss/draw і не годяться для неперервного
   dominance-рахунку, тож свої ~120-150 рядків все одно потрібні).
   ```ts
   export const GLICKO2_SCALE = 173.7178;
   export const GLICKO2_TAU = 0.5;
   export type Glicko2Rating = { rating: number; rd: number; volatility: number };
   export const GLICKO2_DEFAULT: Glicko2Rating = { rating: 1500, rd: 350, volatility: 0.06 };
   export type Glicko2Result = { opponent: Glicko2Rating; score: number };
   export function updateGlicko2Period(player: Glicko2Rating, results: Glicko2Result[], tau?: number): Glicko2Rating;
   export function conservativeRating(r: Glicko2Rating, k?: number): number; // default k=2
   ```
   Внутрішнє (без експорту): конвертація шкали, `g(phi)`, `expectedScore`, дисперсія `v`, дельта
   `Δ`, і ітеративний пошук volatility за алгоритмом Іллінойса з оригінальної статті Glickman'а —
   єдина справді "хитра" частина, переносити треба точно за формулами, без імпровізації.
   **Тест проти офіційного прикладу Glickman'а**: гравець (rating 1500, RD 200, volatility 0.06)
   проти трьох суперників (1400,30)/(1550,100)/(1700,300), результати win/loss/loss (бінарні
   рахунки, без dominance) → очікується rating≈1464.06, RD≈151.52, volatility≈0.05999. Плюс:
   порожній список результатів лише інфлює RD; більший dominance проти рівного суперника дає
   строго більший приріст, ніж вузька перемога.

3. **`src/lib/rating/openskill.ts`** + `openskill.test.ts` — обгортка над новою npm-залежністю
   `openskill` (TypeScript, MIT).
   ```ts
   import { rating, rate, ordinal } from "openskill";
   export type OpenSkillRating = { mu: number; sigma: number };
   export const OPENSKILL_DEFAULT: OpenSkillRating = rating();
   export function updateDoublesMatch(
     teamA: [OpenSkillRating, OpenSkillRating],
     teamB: [OpenSkillRating, OpenSkillRating],
     winner: "A" | "B",
     gamesA: number,
     gamesB: number,
   ): { teamA: [OpenSkillRating, OpenSkillRating]; teamB: [OpenSkillRating, OpenSkillRating] };
   export function displayRating(mu: number): number;
   export function displaySpread(sigma: number): number; // sigma * DISPLAY_SCALE, no offset
   export function conservativeOrdinal(r: OpenSkillRating): number; // displayRating(ordinal(r, { z: 3 }))
   ```
   Реалізація передає `gamesA`/`gamesB` напряму в `rate()` як `score`, з `margin = 1` (гейм) —
   переможець завжди йде окремо через `rank`, ніколи не виводиться з `score` (та сама причина, що
   й клемп у `dominance.ts`). Тест: рахунок у межах `margin` (напр. 7-6) дає результат, побайтово
   ідентичний "чистому" виклику `rate()` без `score`/`margin` — це якір проти регресій. "Суха"
   перемога дає строго більший `|Δmu|`, ніж вузька. Партнери з однаковою sigma рухаються на
   однакову дельту; партнер з більшою sigma (менш стабільний) отримує більшу частку зміни.
   `npm i openskill` не додав нічого в `allowScripts` — пакет чистий TS/JS, без postinstall-скриптів.

4. **`src/lib/rating/engine.ts`** + `engine.test.ts` — чиста оркестрація, переграє всю історію.
   ```ts
   export type RatingMatchRow = {
     id: string;
     tournamentId: string;
     tournamentStartDate: Date;
     winnerSide: "A" | "B";
     createdAt: Date;
     players: { side: "A" | "B"; playerId: string }[]; // 1/сторона одиночні, 2/сторона парні
     sets: { sideAGames: number; sideBGames: number }[];
   };
   export type SinglesRatingRow = { playerId: string; rating: Glicko2Rating; matchesPlayed: number };
   export type DoublesRatingRow = { playerId: string; rating: OpenSkillRating; matchesPlayed: number };
   export function computeSinglesRatings(rows: RatingMatchRow[]): Map<string, SinglesRatingRow>;
   export function computeDoublesRatings(rows: RatingMatchRow[]): Map<string, DoublesRatingRow>;
   ```
   `computeSinglesRatings`: групуємо рядки по `tournamentId`, групи йдуть за `tournamentStartDate`
   за зростанням; всередині групи будуємо для кожного гравця `Glicko2Result[]` за **до-періодними**
   знімками суперників, застосовуємо `updateGlicko2Period` до всіх, хто грав у періоді, плюс
   гілку "без ігор" до раніше бачених гравців, які пропустили період; коміт одразу по всьому
   періоду.
   `computeDoublesRatings`: сортуємо рядки за `(tournamentStartDate, createdAt, id)`, йдемо
   послідовно, беремо поточний рейтинг кожного з 4 гравців (або `OPENSKILL_DEFAULT` для першої
   появи), рахуємо `dominance`, викликаємо `updateDoublesMatch`, записуємо назад, збільшуємо
   `matchesPlayed`.
   Тест на вручну побудованій багатотурнірній історії кількох гравців з розрахованим очікуваним
   порядком; гравець, що пропустив турнір, у якому раніше грав, отримує лише інфляцію RD; партнери
   в парі завжди рухаються разом; матчі одного періоду обробляються в задокументованому
   детермінованому порядку.

5. **`src/lib/rating/ratings-data.ts`** — кешована вибірка + публічне API, точно за патерном
   `src/lib/stats.ts`:
   ```ts
   import { unstable_cache } from "next/cache";
   import { prisma } from "@/lib/db";
   import { STATS_CACHE_TAG } from "@/lib/stats";
   // вибірка через prisma.match.findMany({ where: { status: "COMPLETED", winnerSide: { not: null }, matchType }, select: { id, tournamentId, tournament: { select: { startDate: true } }, winnerSide, createdAt, players: { select: { side, playerId } }, sets: { select: { sideAGames, sideBGames } } } }), обгорнуто в unstable_cache з { tags: [STATS_CACHE_TAG], revalidate: 60 }
   export async function getSinglesRatings(): Promise<SinglesRatingRow[]>; // сортування за conservativeRating desc
   export async function getDoublesRatings(): Promise<DoublesRatingRow[]>; // сортування за conservativeOrdinal desc
   ```

   покривають.

### Текст пояснення (українською, простою мовою — чернетка для уточнення під час реалізації)

1. **Що таке рейтинг** — "Рейтинг — це число, яке показує приблизну силу гравця на основі
   результатів усіх його матчів, а не лише кількості перемог. Перемога над сильним суперником
   піднімає рейтинг більше, ніж перемога над слабшим; поразка від сильного суперника опускає його
   менше, ніж поразка від слабшого."
2. **Чому одиночний і парний рейтинги не можна порівнювати** — "Одиночний і парний рейтинг
   рахуються двома різними математичними методами і показані в схожому діапазоні чисел лише для
   зручності — це не означає, що вони порівнянні. Порівнювати можна тільки одиночний рейтинг з
   одиночним, і парний з парним."
3. **Як враховується рахунок геймів** — "Перемога 6:0, 6:0 піднімає рейтинг сильніше, ніж перемога
   7:6 у вирішальному сеті — система враховує не лише сам факт перемоги, а й те, наскільки
   впевненою вона була."
4. **Чому в парі партнери можуть отримувати різну зміну рейтингу** — "У парних матчах неможливо
   напряму визначити, хто з двох партнерів заслуговує більше 'заслуги' за перемогу — тож зміна
   ділиться між ними залежно від того, наскільки система ще не впевнена в кожному: новачок у парі
   'рухається' сильніше за результатом матчу, ніж досвідчений партнер поруч."
5. **Чому в нових або тих, хто рідко грає, рейтинг менш стабільний** — "Поруч із рейтингом стоїть
   позначка '±...' — вона показує, наскільки система ще не впевнена в реальному рівні гравця. Що
   більше матчів гравець зіграв нещодавно, то менше коливається його рейтинг від одного
   результату."
6. **Чому парний рейтинг не змінюється від перерви так, як одиночний** — "Одиночний рейтинг
   поступово стає менш точним (позначка '±' зростає), якщо гравець довго не грає турніри. Парний
   рейтинг цього не робить — він змінюється лише тоді, коли гравець фактично зіграв матч."

## Свідомо поза межами цього кроку

- Без збереженої історії рейтингу (графік), без адмінської кнопки "перерахувати" (нічого
  перераховувати — все завжди актуальне через `unstable_cache`).
- Без змін у `src/app/players/[id]/page.tsx` (профіль гравця). Плитка рейтингу в стилі `StatCard`
  там — природний наступний крок, але `StatCard` зараз приватний хелпер саме в цьому файлі, не
  винесений окремо — треба спершу винести. Поки не робимо.
- `src/lib/site.ts` — пункт меню "Рейтинг" на `/rating` вже доданий цієї сесії, змін не потрібно.

## Залежності

- Додати `openskill` (npm, ліцензія MIT) у `package.json`. Для одиночних нічого нового — Glicko-2
  написаний вручну.

## Верифікація

1. Нові юніт-тести (`dominance.test.ts`, `glicko2.test.ts`, `openskill.test.ts`, `engine.test.ts`)
   — `npx vitest run src/lib/rating`. `glicko2.test.ts` має точно відтворювати офіційний приклад
   Glickman'а (rating≈1464.06, RD≈151.52, volatility≈0.05999).
2. `npm run test` (весь набір), `npm run lint`, `npx tsc --noEmit` — те саме, що й CI.
3. Вручну: `npm run dev`, відкрити `/rating` на реальних даних — обидві таблиці заповнюються,
   порядок виглядає логічно (гравець, що всіх обіграв 6:0, — вгорі), блоки `<details>`
   розкриваються, перемикач `?format=` зберігає стан через URL, як і на `/leaderboard`.
4. Перевірити живу інвалідацію: відредагувати рахунок завершеного матчу в адмінці, переконатись,
   що `/rating` оновлюється без додаткового коду — це вже покрито наявними викликами
   `updateTag(STATS_CACHE_TAG)` у `matches.ts`, бо нова вибірка перевикористовує той самий тег.
