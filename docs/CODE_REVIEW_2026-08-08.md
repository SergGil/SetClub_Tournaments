# Повне рев'ю застосунку — 2026-08-08

> **Статус: усі пункти нижче реалізовано** того ж дня — див.
> [docs/CHANGELOG.md](CHANGELOG.md)'s "Повне рев'ю застосунку: усунення знахідок" за 2026-08-08.
> Документ лишається як знімок самого рев'ю (що знайшли й чому це важливо), а не як список
> відкритих задач.

Глибоке рев'ю всього кодового бази (357 файлів) п'ятьма паралельними агентами, кожен —
окремий шар: server actions/безпека, дані/Prisma, рейтинг-движок і турнірна логіка, фронтенд,
інфра/CI/R2. Нічого не змінено — це чистий аналіз "на баги та архітектурні покращення", запит
користувача. Загальний висновок: кодова база в дуже хорошому стані (продумані коментарі,
консистентні патерни, сильне тестове покриття для tricky-логіки), знахідки нижче — це
винятки з інакше добре витриманих правил, а не системні проблеми.

Легенда серйозності: 🔴 High · 🟡 Medium · ⚪ Low.

## 1. Баги / коректність

### 🔴 Час завершення матчу показується в серверному часовому поясі, не київському
`src/components/match-summary.tsx:363-368` викликає
`new Date(match.completedAt).toLocaleTimeString("uk-UA", {...})` без `timeZone: "Europe/Kyiv"`.
На Vercel (UTC-хост) це зсуває показаний час на 2-3 години від реального київського — саме той
клас багу, для якого існує `src/lib/date-format.ts` (`formatDateKyiv` явно фіксує таймзону).
`MatchSummary` використовується скрізь (головна, матчі, турніри, адмінка) — це видимий усім
некоректний час. Не покрито тестом (`tests/components/match-summary.test.tsx` не ставить
`completedAt`).

Той самий баг, менш критично (адмінка): `src/app/admin/audit/page.tsx:61-64` —
`entry.createdAt.toLocaleString("uk-UA", {...})` без таймзони, підриває саму мету сторінки
("хто, що і коли змінив").

**Фікс**: обидва місця мають йти через `formatDateKyiv`/еквівалент з `date-format.ts` замість
прямого `toLocaleTimeString`/`toLocaleString`.

### 🟡 `updateMatchAction` не перевіряє, що гравці — учасники турніру
`src/lib/actions/matches.ts:166-229`. `createMatchAction` явно ревалідує кожен
`sideAPlayerIds`/`sideBPlayerIds` проти `TournamentParticipant` (бо zod перевіряє лише форму
ID, не належність) — `updateMatchAction` парсить ту саму схему, але цю перевірку пропускає.
Плюс у `catch`-блоці (166-251) немає гілки `isForeignKeyError`, на відміну від
`createMatchAction` — неіснуючий `playerId` дасть непійманий P2003 замість дружнього
повідомлення. UI обмежує `<select>` ростером, тож потрібен прямий виклик Server Function в
обхід UI — але саме таку загрозу код в іншому місці (`match-randomize-shared.ts:12-13`) явно
враховує. Не покрито тестом.

### 🟡 GROUPS12: зняття гравця з 3-го місця групи назавжди залишає міні-групу "недограною"
`src/lib/bracket-advancement.ts` + `src/lib/groups12-playoff-bracket.ts`. Якщо зняти (withdraw)
гравця, який фінішує 3-м у своїй групі формату "4 групи по 3 + плейофф", у групі лишається
лише 2 незнятих кандидати — `sourceRank: 3` назавжди резолвиться в `null`, відповідний
`MINI_x`-матч довічно лишається з порожньою стороною, `isRoundRobinComplete` для міні-групи
"9-12 місце" ніколи не стає `true`, і зведена таблиця 1-12 для цього турніру назавжди
позначена неповною. Очки Set Club не страждають (9-12 місця мають однакове flat-значення), це
суто косметична, але цілком реалістична адмінська дія — і `docs/GROUPS12_PLAYOFF.md`'s
"Відомі обмеження" про це не згадує. Не покрито тестом (`bracket-advancement.test.ts`/
`groups12-playoff-bracket.test.ts` тестують зняття лише в плоскій 3-гравцевій групі, не саме
rank-3 у 4-груповому форматі).

### ⚪ `computeMatchPoints` дає 0-0 очок для `retired`-матчу без жодного сету
`src/lib/match-result.ts:106-119`. Якщо матч завершено як `retired` до завершення першого сету
(`sets: []` — можливо за коментарем схеми "sets і рахунок не мусять формувати легальний
результат"), перемога/поразка зараховується у W/L, але 0 очок нараховується обом сторонам у
турнірній таблиці. Малоймовірно на практиці (UI, ймовірно, вимагає хоч частковий сет), але сам
`computeMatchPoints` цього не гарантує. Немає тесту на порожній `sets`.

### ⚪ CSV-експорт не використовує нікнейми (`displayName()`), на відміну від решти застосунку
`src/lib/export/matches-csv.ts:21` і `src/lib/export/participants-csv.ts` беруть
`p.player.name` напряму замість `displayName()`, хоча `nickname` "показується замість `name`
майже всюди" (коментар у `schema.prisma:122`). Адмін, що поставив нікнейм для розрізнення
тезок, у CSV побачить неправильне/дублююче ім'я.

## 2. Безпека

### 🟡 Presigned R2 PUT не прив'язує Content-Type/розмір — це лише клієнтська порада
`src/lib/r2.ts:43-50`. Емпірично перевірено (`X-Amz-SignedHeaders=host` — і все): ні
`Content-Type`, ні розмір не входять у підпис. `ALLOWED_PHOTO_CONTENT_TYPES` та
`MAX_PHOTO_BYTES` (20MB, `src/lib/validation/photo.ts:6-8`) — перевірки лише на боці клієнта
(`photo-upload-dialog.tsx:74-76`) і при генерації URL. Той, хто отримав presigned URL
(5-хвилинне вікно), може `PUT` довільний `Content-Type` чи необмежений розмір файлу.
Експлуатабельність низька (потрібна вже автентифікована ADMIN-сесія), але це реальний розрив
між задокументованою політикою (`docs/PHOTOS.md:61-62`, "20MB — лише запобіжник") і тим, що
насправді забезпечено на сервері.

### ⚪ `confirmPhotoUploadAction` не перевіряє, що `key` реально видано для цього турніру
`src/lib/actions/photos.ts:13-23`, `src/lib/validation/photo.ts:10-16`. `key` — це просто
непорожній рядок, нічим не прив'язаний до `tournamentId`-префіксу з presign-роуту чи до сесії,
яка його отримала. Будь-який адмін може напряму викликати Server Action з чужим відомим `key`
(ключі не секретні — видно у публічних URL фото) і створити другий `Photo`-рядок на той самий
R2-об'єкт → видалення одного рядка (`deletePhotoAction` видаляє й сам R2-об'єкт) залишає другий
рядок "битим" назавжди.

### ⚪ Інші дрібні неконсистентності в server actions
- `addParticipantAction` (`src/lib/actions/tournaments.ts:246-264`) — єдина дія такого типу без
  try/catch навколо транзакції; неспіймана P2003-помилка при конкурентному видаленні дасть
  гірший UX, ніж усюди інде (не витік стектрейсу — Next сам санітизує).
- `commitSinglesGroupsAction` (`src/lib/actions/randomize-singles.ts:279-284`) не фільтрує
  `withdrawnAt: null` при перевірці ростера — на відміну від усіх сусідніх commit-дій. Вузьке
  вікно гонки між превʼю жеребкування і коммітом.
- `withdrawParticipantAction` (`src/lib/actions/tournaments.ts:338-462`) не має advisory-lock,
  на відміну від усіх commit-дій рандомізаторів (які явно захищені саме від подвійного кліку).
  Ймовірно ідемпотентно на практиці, але інконсистентно із захисним патерном решти файлу.

## 3. Залежності / інфраструктура

### 🟡 `next@16.2.12` тягне вразливі `postcss`/`sharp` у власному дереві залежностей
Підтверджено `npm audit`: `node_modules/next/node_modules/postcss@8.4.31` (CSS-stringify XSS,
розкриття source-map) та `sharp@0.34.5` (успадковані libvips CVE) — останній тепер активно
використовується в проді для обробки фото (`next/image` проти `*.r2.dev`). У парі з відсутньою
серверною валідацією типу/розміру (див. вище) — крафтоване зображення пройде через вразливий
libvips-кодек. `npm audit fix --force` показує, що обидві проблеми вирішує `next@16.3.0`, вже
"Latest" за `npm outdated` — некритичне патч-оновлення, варте зробити.

### ⚪ Бекапи БД не зашифровані за замовчуванням
`.github/workflows/db-backup.yml` шифрує дамп лише якщо заданий секрет
`BACKUP_ENCRYPTION_PASSPHRASE`; без нього дампи з реальними email гравців лежать як звичайний
`.sql.gz`-артефакт (захищений лише правами доступу до репо, 30 днів). Свідомий компроміс
(закоментовано в файлі) — фіксується як нагадування, не як помилка.

### ⚪ `e2e`-job у CI можна мовчки пропустити
`.github/workflows/ci.yml`'s `check-e2e-secret` перетворює весь `e2e`-job на no-op (не на
provalilure), якщо `CI_DATABASE_URL` не заданий як секрет репо. Якщо секрет колись зникне —
PR змержаться без жодного запуску e2e і без червоного хреста, що це помітив би.

### ⚪ e2e ганяється проти `next dev`, не проти зібраного застосунку
`playwright.config.ts:17-22` піднімає `npm run dev`. CI's `build`-job доводить лише, що
`next build` проходить (і саме це коректно ловить клас багів з `"use server"`-експортами — див.
пам'ять проєкту), але ніколи не запускає зібраний вихід і не б'є по роутах — residual сліпа
зона для суто рантайм-різниці build vs dev.

### ⚪ README не згадує R2-змінні оточення
`README.md`'s список змінних для розробки не включає п'ять `R2_*` (вони є, повно, в
`docs/PHOTOS.md`, але не залінковані з README setup-секції) — хтось, хто піде лише за README,
впаде на "R2_ACCOUNT_ID is not set" при першому дотику до фото.

### ⚪ Немає тестів на `/api/photos/presign`
Ні unit (роут виключено з покриття навмисно), ні e2e (перевірено всі 5 e2e-спеків — фото/
галерея взагалі не покриті e2e: аплоад, видалення, `/gallery`, `/gallery/[id]`).

## 4. Архітектурні спостереження (не баги)

Позитивне, варте зафіксувати як "працює правильно, не чіпати":
- **Авторизація** централізована в `src/app/admin/layout.tsx` (реальна DB-перевірка), `proxy.ts`
  свідомо робить лише дешеву cookie-presence-перевірку (задокументовано чому — минулий інцидент
  з падінням /admin при збої БД), і кожна mutating-дія додатково сама викликає
  `requireAdmin()`/`requireUser()` — немає покладання лише на UI чи Proxy.
- **`"use server"` async-only обмеження** дотримано всюди: єдиний файл, якому потрібен
  non-async експорт (`CascadeResetPendingError`), свідомо не має директиви `"use server"` і
  документує чому (`src/lib/actions/bracket-snapshot.ts:4-16`) — саме той клас бага, який раніше
  ловили в проді, тут явно й правильно оброблено.
- **Concurrency-безпека**: `pg_advisory_xact_lock` на коміти рандомізаторів,
  `@updatedAt`-guarded optimistic concurrency на збереження рахунку
  (`StaleScoreConflictError`), транзакційний rebuild рейтингових знімків — все послідовно і з
  коментарями, що саме за перегони кожен механізм закриває.
- **Glicko-2/OpenSkill математика** звірена рядок-в-рядок з канонічним алгоритмом (включно з
  Illinois-модифікацією волатильності) — без розбіжностей.
- **Немає N+1**, немає SQL-injection поверхні (жодного `$queryRaw` в проєкті), CSV-експорт
  коректно захищений від formula injection (OWASP-патерн) з BOM для кирилиці.
- **XSS**: жодного `dangerouslySetInnerHTML` на користувацькому контенті в усьому проєкті.

Речі, варті уваги на майбутнє (не терміново):
- **Немає індексів на `Match.status`/`winnerSide`/`scheduledDate`/`completedAt`** — майже
  кожен hot-path запит фільтрує саме по них, є лише `@@index([tournamentId])`. Full-scan+sort
  на кожен такий запит; прийнятно при поточному масштабі клубу, але перше, що варто додати,
  якщо дані виростуть.
- **`getPlayersPage`** (`src/lib/queries/players.ts:47-69`) вичитує всю таблицю `Player` в JS
  для сортування через `Intl.Collator("uk")` перед зрізанням до `limit` — задокументовано як
  свідомий компроміс під поточний масштаб, єдине місце такого патерну.
- **`load-more.ts`** — offset/`take`-based пагінація, не курсорна; конкурентний insert між
  кліками теоретично може зсунути/задублювати межовий рядок. Прийнятний trade-off при
  поточному масштабі.
- Дрібна a11y-неконсистентність: `rating-history-chart.tsx`'s точки графіка не
  keyboard-reachable (на відміну від `rating-distribution-chart.tsx`, де це зроблено кнопками);
  `photo-lightbox.tsx` не має навігації стрілками (Prev/Next — фокусовні кнопки, тож не
  порушення, лише відсутність очікуваної зручності).

## Підсумок пріоритетів

Якщо виправляти по одному, у такому порядку віддачі/зусиль:
1. Таймзона в `match-summary.tsx` (і `admin/audit/page.tsx`) — маленький фікс, видимий усім
   користувачам баг.
2. `updateMatchAction` roster-перевірка + `isForeignKeyError` гілка — вирівняти з
   `createMatchAction`.
3. `next` → 16.3.0 (закриває дві CVE в транзитивних `postcss`/`sharp`).
4. Серверна валідація Content-Type/розміру для R2-аплоаду (S3 POST policy з
   `content-length-range` замість голого PUT, або перевірка після факту через `HeadObject`).
5. GROUPS12 rank-3-withdrawal edge case — задокументувати в "Відомі обмеження" мінімум, за
   можливості — виправити резолюцію міні-групи.
6. Решта — дрібні консистентність-фікси (advisory lock на withdraw, try/catch на
   addParticipantAction, withdrawnAt-фільтр на commitSinglesGroupsAction, nickname в CSV).
