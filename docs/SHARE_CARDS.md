# Поділитися результатом — картки для соцмереж

## Контекст

Глибоке дослідження застосунку (окрема сесія, не пов'язана з конкретним багом) виявило кілька
продуктових прогалин, не покритих попередніми code review/UX-аудитами (ті були зосереджені на
формах/таблицях/потоках даних, не на новій функціональності). З короткого списку ідей користувач
обрав одну: можливість «поділитися» результатом матчу чи фінальними місцями турніру як готовою
картинкою — щоб можна було відправити в Telegram/Viber клубний чат чи в Instagram Stories, не
роблячи скріншот сторінки вручну. Перед реалізацією користувачу показали HTML-мокап картки
(Artifact) для затвердження вигляду — фінальний дизайн нижче йому відповідає, з однією свідомою
відмінністю (див. "Очки чи W-L" нижче).

## Архітектура

### Генерація зображення: `next/og` `ImageResponse`, не Canvas/скріншот

Той самий підхід, що вже використовує застосунок для `src/app/icon.tsx`, `src/app/apple-icon.tsx`
і `src/app/manifest-icons/[size]/route.tsx` (усі — через `src/lib/brand-icon.tsx`), просто вперше
застосований до даних, а не статичного брендового значка. `ImageResponse` рендерить JSX+CSS у PNG
на сервері (Satori + resvg під капотом), без headless-браузера чи Canvas на клієнті.

**Кирилиця.** Жоден існуючий `ImageResponse`-виклик у застосунку раніше не рендерив кирилицю
(лише "S"/"SET."/"club"). `@vercel/og` (вендорено в `node_modules/next/dist/compiled/@vercel/og`)
без явної опції `fonts` сам визначає скрипт тексту й довантажує відповідний Google-шрифт
(`loadDynamicAsset`/`loadGoogleFont`) — кирилиця не в явному переліку мов пакета, тож падає у
фолбек `Noto+Sans`, який кирилицю підтримує. Свідомо не бандлимо власний шрифтовий файл (ліміт
`ImageResponse`-бандла — 500KB, зайва binary-залежність) — ціна цього рішення: один мережевий
запит до `fonts.googleapis.com` на "холодний" рендер (перший запит з нового serverless-інстансу).
Перевірено вживу (нижче) — кирилиця рендериться коректно.

**Satori — лише flexbox.** Двигун `ImageResponse` підтримує тільки flexbox + обмежений набір CSS
через inline `style`-об'єкти — без Tailwind-класів, без CSS grid. Через це картки написані як
окремі "тупі" JSX-функції, що дублюють візуальний дизайн `MatchSummary`/`PlacedTournamentStandings`
замість того, щоб їх перевикористовувати.

Одна реальна пастка, знайдена лише живим переглядом (не tsc/тестами): **`inset: 0` не працює** —
фоновий градієнт і весь білий текст поверх нього рендерились невидимими (білий текст на
нерозфарбованому/прозорому фоні), доки `inset: 0` не замінили на явні `top/left/right/bottom: 0`.
Якщо додаватимеш нову декоративну абсолютно-позиційовану секцію в ці файли — використовуй лише
довгі CSS-властивості позиціювання, не шорткати.

### Дані окремо від JSX

Кожна картка розділена на:
1. **Чисту функцію даних** (`src/lib/share/match-card-data.ts`, `.../tournament-card-data.ts`) —
   без Satori/JSX, тестована звичайним vitest. `buildMatchShareData`/`buildTournamentShareData`
   повертають `null`, коли показувати нічого (матч не `COMPLETED`, чи турнірні місця ще не
   вирішені) — роут-хендлер тоді віддає 404.
2. **JSX-функцію для `ImageResponse`** (`match-card-image.tsx`, `tournament-card-image.tsx`) — не
   тестується, той самий стандарт, що вже мовчки застосований до `brandIconElement` (жоден
   `ImageResponse`-роут у застосунку не мав тестів до цього моменту).

### Очки чи W-L — свідома відмінність від мокапу

У мокапі, показаному користувачу, подіум турніру був підписаний "балів SET.club" — після
детальнішого читання коду з'ясувалось, що `PlacedStandingsRow.points`
(`src/lib/standings-sort.ts`) — це турнірні "Очки" (`computeMatchPoints`: 2 за виграний
односетовий матч, інакше по 1 за сет), **інша** система підрахунку, ніж клубний рейтинг
SET.club (`src/lib/rating/placement.ts`). Змішувати їх на картці означало б показувати цифру, яка
не збігається з жодною таблицею в самому застосунку. Фінальна картка показує W-L рекорд
(`5-1`) — те саме число, що вже в колонках "Перемог"/"Поразок" `PlacedTournamentStandings`.

### Роути

- `GET /api/share/match/[id]` (`src/app/api/share/match/[id]/route.tsx`) — `getMatchById`
  (новий, `src/lib/queries/matches.ts`) → `buildMatchShareData` → `ImageResponse`.
- `GET /api/share/tournament/[id]` (`.../tournament/[id]/route.tsx`) — `getTournamentById` +
  `getTournamentStandingsRows` (ті самі виклики, що вже робить `/tournaments/[id]`) →
  `buildTournamentShareData` → `ImageResponse`.
- Обидва публічні (без `requireAdmin`/сесії) — та сама інформація вже видима на самій сторінці
  матчу/турніру; жодних приватних полів (email/userId) у вибірку немає. 404 (`NextResponse.json`),
  якщо матч/турнір не знайдено або результат ще не вирішено — навмисно, щоб посилання на
  незавершений матч не генерувало картку з довільними/нульовими даними.

### `ShareResultButton` — перша download/share-інтеграція в застосунку

`src/components/share-result-button.tsx` — спільний клієнтський компонент для обох контекстів
(матч у `MatchSummary`, подіум у `TournamentStandingsSection`), з `Dialog`/`DialogTrigger`
(Base UI, той самий `render=`-патерн, що й `FormatRulesButton`). Прев'ю — простий `<img
src={imageUrl}>`, браузер сам довантажує PNG.

- **Завантажити** — `fetch` → `blob()` → `URL.createObjectURL` → тимчасовий `<a download>` → клік
  → **`revokeObjectURL` одразу після** (той самий урок з витоку ObjectURL, вже виправленого в
  `news-photo-field.tsx`).
- **Поділитися…** — Web Share API (`navigator.share`/`canShare({files})`), лише коли браузер це
  підтримує. Виявлення підтримки — через `useSyncExternalStore` з фіксованим `getServerSnapshot
  () => false` (не `useEffect`+`useState`): цей репозиторій має активне ESLint-правило
  `react-hooks/set-state-in-effect`, яке забороняє синхронний `setState` всередині ефекту саме
  для такого класу "прочитати браузерну можливість після монтування" — `useSyncExternalStore` з
  no-op `subscribe` (можливість не змінюється за час життя сторінки) — правильний інструмент, той
  самий, що вже застосований у `theme-toggle.tsx`.
- `AbortError` (юзер закрив системний shareaheet) — тихо ігнорується; будь-яка інша помилка —
  `toast.error` (sonner).

## Верифікація

- `npx tsc --noEmit`, `npm run lint`, `npx vitest run` (939 тестів, +15 нових), `npm run build` —
  усі чисті.
- **Живий перегляд у браузері (обов'язковий для цього класу фічі — жоден тест не ловить
  кирилицю/Satori-специфічні CSS-пастки):**
  - Перша спроба показала повністю невидимий білий текст на нерендереному фоні — знайдено й
    виправлено `inset: 0` баг (див. вище) через прямий `curl`+перегляд PNG.
  - Після фіксу: кирилиця рендериться чисто (перевірено на реальних іменах з бойової БД —
    "Андрєєв Олександр", "Кулєш Ірина" тощо), тайбрейк-бейдж, парний матч (2 імені на сторону),
    подіум 1-2-3 з кольорами gold/silver/bronze і коректним W-L.
  - Playwright проти реального dev-сервера (тимчасовий, видалений після перевірки): клік
    "Поділитися" відкриває діалог, `<img>` реально довантажується (`naturalWidth === 1200`, не
    просто присутній `src`), "Завантажити" видає реальну подію завантаження з очікуваним іменем
    файлу `set-club-{match,tournament}-{id}.png`.
  - Web Share API не перевірявся живим кліком (headless Chromium його не підтримує) — код-шлях
    покритий unit-тестом компонента (`tests/components/share-result-button.test.tsx`) з мокнутим
    `navigator.share`/`canShare`.
