# Онбординг нового учасника (план, не реалізовано)

## Контекст

Перший вхід через Google створює `User` через `createUser` (`src/lib/auth.ts` →
`provisionNewUser`, `src/lib/auth-provisioning.ts`) — подія спрацьовує рівно один раз. Далі
новий учасник одразу бачить повний сайт з усією глибиною даних: два незалежні рейтинги
(Glicko-2/OpenSkill + власні Set Club бали), поріг "рейтинг ще формується" до
`PROVISIONAL_MATCH_THRESHOLD` завершених матчів (`src/lib/rating/ratings-data.ts`), head-to-head
матрицю, розділення Теніс/Падел/Кава в навігації. Немає жодного пояснення "з чого почати" —
ризик, що новачок або не зрозуміє, чому його немає в таблиці рейтингу, або просто не знайде
власний профіль.

## Дизайн

**Свідомо не повноцінний product tour** (підсвічування елементів по кроках, бібліотека на кшталт
Shepherd/Intro.js) — крихко проти вже складної логіки `nav.tsx` (адмін-скоуп, гейтинг
Padel/Coffee-секцій, які й так плановані на структурну переробку в пункті 7
`docs/DESIGN_ROADMAP_2026.md`) і зайва вага для сайту, який свідомо відмовився від "маркетингових"
патернів (див. розділ "Свідомо відкинуто" в тому ж документі).

**Пропозиція: одноразове привітальне модальне вікно** одразу після першого входу — 3-4 короткі
слайди/секції (не окрема сторінка, легкий компонент типу вже наявних діалогів у
`src/components/ui/`):

1. Що таке рейтинг клубу — дві незалежні шкали (Glicko-2/OpenSkill і Set Club бали), і чому
   свіжий гравець спершу в списку "рейтинг ще формується" (пояснити поріг у матчах — той самий
   текст, що вже є в інформері на `/rating` для цього випадку, можна перевикористати formulation).
2. Де свій профіль і особисті зустрічі (head-to-head) — пряме посилання на `/players/[id]`.
3. Структура сайту — Теніс/Падел/Кава як окремі розділи, одиночні/парні турніри, групи+плейоф.
4. (тільки якщо роль `MEMBER`, не `ADMIN`) — коротко, що учасник тільки переглядає, рахунок
   вносить адміністратор.

**Схема.** Новий nullable стовпець `User.onboardedAt DateTime?` — той самий патерн, що
`withdrawnAt`/`nickname` (nullable, без default, timestamp = коли закрив модалку). Не на `Player`
— `Player` може ще не існувати на момент першого входу (авто-лінкування за email у
`provisionSignIn` трапляється, але не гарантовано для кожного нового User), а `User` існує завжди
з моменту `createUser`.

**Показ.** Клієнтський компонент перевіряє `session.user.onboardedAt === null` (додати поле в
`session` callback у `src/lib/auth.ts`, за прикладом уже наявних `role`/`domains`) і рендерить
модалку один раз за сесію завантаження layout. Закриття (хрестик або "Зрозуміло") викликає
server action, що проставляє `onboardedAt = now()` — модалка більше ніколи не з'являється
автоматично; окремим пунктом можна лишити "Довідка" в футері/меню, яка відкриває той самий контент
вручну в будь-який момент.

## Код/файли (орієнтовно)

- `prisma/schema.prisma` — `User.onboardedAt DateTime?` + міграція.
- `src/lib/auth.ts` — `session.user.onboardedAt` у `session` callback.
- `src/lib/actions/onboarding.ts` — `markOnboardedAction()`, той самий "use server" патерн, що
  інші прості дії; **обов'язково перевірити прод-білдом** (`npm run build` +
  ручна перевірка на dev/prod — за уроком з "use server"-файлами, які проходять `tsc`/`vitest`,
  але падають у проді, див. записану пам'ять про це).
- `src/components/onboarding-modal.tsx` — клієнтський компонент, 3-4 секції, кнопка закриття.
- Підключення в `src/app/layout.tsx` (поруч із рештою глобальних клієнтських елементів nav'у).

**Скоуп v1**: тільки web. Мобільний застосунок (`mobile/`) має власний Google sign-in обмін
(`src/app/api/v1/auth/google`, той самий `provisionSignIn`), можна підняти той самий прапорець
через API пізніше — не блокер для web-версії.

## Відкриті питання

1. Контент слайдів — фінальні формулювання варто звірити з живим текстом інформерів на `/rating`,
   щоб не суперечити.
2. Чи потрібна ручна кнопка "Показати знову" (довідка), чи одноразового показу достатньо?
3. Мобільний онбординг — окремим спринтом чи взагалі не потрібен (нативний апк може мати власний
   simpler-first-run флоу)?
