# Адмінські групи (1-6) в турнірах

## Контекст

В SINGLES-турнірах адмін може вручну розподілити учасників по групах 1-6 незалежно від сіяності
(`TournamentParticipant.group`) — рандомайзер тоді формує кругову систему окремо всередині кожної
групи (стратегія "За групами"), а таблиця результатів турніру показує групи як окремі блоки.
У DOUBLES цієї можливості довгий час не було: `GroupSelect` у ростері рендерився лише для
`format === "SINGLES"`, рандомайзер парних завжди грав один загальний тур на весь ростер, а
`getTeamRows` у `tournament-standings.ts` завжди повертав плаский список команд.

Користувач попросив повний аналог для парних турнірів — і явно підтвердив, що "заздалегідь
визначені пари" (лока-пара вручну) мають працювати й у режимі груп, а не тільки в звичайному
розіграші.

## Ключове рішення: як групи "гравців" узгоджуються з групами "команд"

Групи призначаються **гравцям** індивідуально (той самий `TournamentParticipant.group`, що й для
SINGLES) — окремої сутності "команда"/"пара" в схемі БД немає, пара завжди виводиться на льоту з
того, хто фактично зіграв на одній стороні матчу (див. `getTeamRows`). Тому команда належить групі
лише тоді, коли **обидва** її гравці мають однакову групу — інакше команда лишається поза
групуванням (так само, як негрупований гравець просто не потрапляє в жоден блок "За групами" у
SINGLES).

Рандомайзер "За групами" для парних формує пари (сіяний+несіяний кошик, як і в звичайному режимі)
**окремо всередині кожної групи** — команди з різних груп ніколи не грають між собою:
`buildCustomGroupsDoublesRoundRobin` (`src/lib/randomize-pairs.ts`) бакетить учасників і
заздалегідь визначені пари за групою, і для кожної групи викликає вже наявний
`buildRandomDoublesPairing` без змін — жодного дублювання логіки формування пар.

### Заздалегідь визначені пари в режимі груп

Якщо обидва гравці заздалегідь визначеної пари вже мають групу — і вона однакова — пара належить
цій групі. Якщо групи різні — помилка ("Гравці заздалегідь визначеної пари в різних групах —
виправте групи в ростері"), бо системі нема з чого вибрати. Якщо один/обидва гравці ще без групи —
`assignUngroupedDoublesToGroups` (мірор `assignUngroupedToGroups` з singles) трактує пару як
**один юніт** при збалансованому випадковому розподілі по вже активних групах — обидва гравці
завжди йдуть в ту саму групу разом, а не розкидаються окремо, що зламало б пару.

## Таблиця результатів

`getTournamentStandingsRows`, DOUBLES-гілка: команда групується, якщо `row.key.split("+")`
(playerId1+playerId2) резолвиться в однакову непусту групу для обох гравців. Поріг для реального
спліту — ≥2 групи в грі, той самий, що вже діяв для SINGLES/MIXED (одна група на весь ростер не
дає жодної переваги над пласким списком).

## Код/файли

- `src/lib/randomize-pairs.ts` — `doublesRandomizeStrategyValues`, `assignUngroupedDoublesToGroups`,
  `buildCustomGroupsDoublesRoundRobin`.
- `src/lib/actions/randomize-doubles.ts` — `drawDoublesGroupsAction`/`commitDoublesGroupsAction`
  (мірор `drawSinglesGroupsAction`/`commitSinglesGroupsAction`), спільна валідація `fixedPairs`
  винесена в `validateFixedPairs`.
- `src/components/admin/tournament-roster.tsx` — `GroupSelect` тепер і для DOUBLES.
- `src/components/admin/randomize-matches-button.tsx` — стратегія-select + групований reveal-UI.
- `src/lib/tournament-standings.ts` — групування DOUBLES-гілки за спільною групою пари гравців.

MIXED свідомо поза скоупом цієї зміни — там `GroupSelect` і далі не показується, хоча
`getTournamentStandingsRows` технічно вже підтримує групування для MIXED (той самий шлях, що й
SINGLES) відтоді, як цю фічу вперше зробили.

## Верифікація

`npx tsc --noEmit`, `npm run lint`, повний `npm run test` (618/618) і `npm run build` — усі чисті.
Юніт-тести покривають: пара не розколюється між групами при auto-balance, конфлікт груп у
заздалегідь визначеній парі дає помилку, матчі й teams ніколи не перетинають групу, таблиця
виключає команду зі змішаними групами гравців з усіх блоків.

## Рандомайзер "Групи зі сіяністю" (2026-10-08)

Нова стратегія одиночного рандомайзера (`SEEDED_GROUPS`, теніс і падел): адмін вказує кількість
груп (2–6), а сіяні й несіяні випадково розкидаються по групах **порівну** — напр. 12 гравців
(8 сіяних + 4 несіяних) у 4 групи = по 2 сіяних + 1 несіяний у кожній; далі кожна група грає
круговою системою лише всередині себе (12 матчів). Без плей-офф.

- `assignSeededGroups(participants, groupCount)` (`src/lib/randomize-pairs.ts`): сіяні роздаються
  по колу в довільному порядку груп, потім несіяні — у групи з найменшою кількістю гравців (серед
  рівних — випадково). Розміри груп і кількість сіяних у групах відрізняються не більш ніж на 1.
  `seededGroupSizes` — детермінований мультинабір розмірів для прев'ю кількості матчів у UI.
- `drawSinglesSeededGroupsAction` / `drawPadelSinglesSeededGroupsAction` — read-only розіграш
  (повертає той самий `SinglesGroupDrawState`, що й "За групами", тож UI-анімація розподілу не
  змінилась; сіяні розкриваються першими). Вимоги: кількість груп 2–6, щонайменше 1 сіяний,
  щонайменше по 2 гравці на групу. Групи, призначені вручну в ростері, ігноруються й
  перезаписуються.
- Збереження — наявні `commitSinglesGroupsAction` / `commitPadelSinglesGroupsAction` (виставляють
  `group` учасникам і замінюють матчі в одній транзакції); новий необов'язковий аргумент
  `strategy` лише підписує запис в audit-журналі. Групові таблиці на сторінці турніру — ті самі,
  що для "За групами" (групи зберігаються як звичайні `group` учасників).
- UI: пункт "Групи зі сіяністю" з'являється при ≥ 4 учасниках і ≥ 1 сіяному, поруч — вибір
  кількості груп (за замовчуванням ~по 3 гравці в групі).
- Мобільний API цього розіграшу не має (як і не мав нового формату "4 групи по 3 + плей-офф"
  в окремому ендпоінті — лише існуючий `groups/draw|commit` для "За групами").
